Add --coverage to run-harness.sh (passes -DCN105_COVERAGE=ON; default build dir becomes tests/unit/build-cov when --coverage is given without --build-dir; builds cn105_headers_<v> next to cn105_char_<v>).
2. Header translation units (D-10: every .h under components/cn105 is in the coverage scope, 0% when no test executes it). Problem: GCC emits an inline function — including a member function defined in a class body — only in a TU that uses it, so a header whose code no test calls produces no gcov record and silently leaves the report, and diff coverage then passes on it with no data. Fix, inside cn105_harness_variant and only when CN105_COVERAGE is ON: file(GLOB CONFIGURE_DEPENDS) the components/cn105/*.h files; for each header write a generated TU into the build tree at header_tu_<v>/<header file name>.cpp (for example header_tu_esp32/cn105_protocol.h.cpp) with file(CONFIGURE) so unchanged content is not rewritten; its content is a one-line comment (generated coverage-only header TU, D-10), an include of cn105.h, then an include of the header itself (all 37 headers have include guards, so cn105.h's own TU is fine). Create OBJECT library cn105_headers_<v> from these generated files, linking harness_flags_<v> for includes and defines, with compile options --coverage and -fkeep-inline-functions (GCC then emits every non-template inline function of every included header, so its lines are recorded as coverable even when nothing calls them); no -fno-access-control (this is production code, D-21). Never link cn105_headers_<v> into any executable and never reference its objects from a test target: forced emission also emits ESPHome and libstdc++ inline functions that may call symbols the harness does not define. gcovr 8.6 reads a .gcno without .gcda as 0% (RESEARCH, verified on an unlinked file), and lines tests do execute are recorded by the TUs that call them; gcovr merges counts per file and line (plan 01-05). Keep it in the default build (not EXCLUDE_FROM_ALL) so a full build compiles it. Defined limits, to state in a comment at the top of the generated-TU block: template code produces lines only where a shipped .cpp or a test instantiates it, and macro bodies are attributed to their expansion site — an uninstantiated template has no object code in the firmware either. If -fkeep-inline-functions makes a header TU fail to compile, stop and report it as a blocking deviation in the SUMMARY; keep every header, the flag and the TU (D-10). No file is added to components/cn105 (D-03). Because the logic lives in cn105_harness_variant, the esp8266 variant of plan 01-03 gets the same instrumentation and header TUs without further CMake work.
  </action>
